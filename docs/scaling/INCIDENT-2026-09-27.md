# Production connectivity incident, September 27, 2026

Current status: production v0.30.1 is live on replacement host 167.172.21.42. The timeline below preserves the original observations. See the recovery entry and HOST_MIGRATION.md for current infrastructure state.

At approximately 22:52 UTC a user reported production not loading. External HTTPS probes intermittently timed out in TCP/TLS connection establishment. Successful requests also took 3–9 seconds, while an unrelated public site responded in 0.1 seconds from the same workstation. Bypassing DNS did not eliminate failures.

Inside the droplet, production API health returned `ok:true`, and nginx served the production page over local HTTPS with status 200 in approximately 0.12 seconds. nginx and both application services were active. The resized guest reports 4 GB RAM and two CPUs, around 2.8 GB available memory, no swap use, low load, and 16 GB free disk. Listener overflow/drop counters were zero. Interface error/drop counters were zero.

Guest kernel counters showed 11,634 retransmitted TCP segments and 3,575 SYN retransmissions since boot. Kernel logs also contain repeated backward clock jumps and delayed work/interrupt warnings. These are evidence of transport/guest timing problems, not proof of a specific DigitalOcean host fault. Outbound HTTPS has also been intermittently slow or timed out.

Earlier temporary DNS experiments were reverted to the original VPC resolver, 10.116.15.254. No network configuration files or routes were changed. No production code rollback is indicated by the current evidence.

Diagnostics were saved privately in `/root/newdrugs-incident/`. A clean reboot at 22:58 UTC restored every enabled service. Public API health and the HTML/JS/CSS returned successfully, and the founder initially confirmed fast access. The improvement was temporary: connection stalls and DNS timeouts returned. Do not mark this incident resolved.

At 23:01 UTC, `newdrugs-worker@dev`, `newdrugs-search@dev` and the prepared-but-unused `newdrugs-search@prod` were stopped to isolate the added services. Production API, dev API, nginx and Mongo remained running. Their units remain enabled, so they will restart on the next boot unless explicitly changed. Dev background processing/search are temporarily unavailable during isolation.

With those services stopped and sampled CPU idle at 92–95%, a five-packet ping to the droplet's gateway (24.144.96.1) lost 60%; a second eight-packet run lost 62.5% with received replies taking 2.2–4.7 seconds. ICMP alone is not definitive, but concurrent TCP connection failures and DNS timeouts support a lower-level connectivity problem. The guest nftables ruleset is empty and iptables built-in policies accept traffic. Routes are unchanged. The user declined contacting DigitalOcean Support. Do not submit a support ticket.

The founder performed a control-panel power cycle around 23:06 UTC. A new boot was verified, with nginx, both APIs, the dev worker and both search services active again. Recovery remained intermittent according to both the founder and external checks. The isolation stops are no longer in effect.

Three independent Globalping HTTPS HEAD probes to `/api/health` at approximately 23:09 UTC returned 200 but took 3.5, 4.0 and 6.5 seconds. TCP connection establishment took 3.0, 2.8 and 4.5 seconds respectively; first-byte times after setup were 107, 21 and 18 milliseconds. Locations were Los Angeles, Buffalo and Ashburn. This corroborates connection-establishment delay outside the founder's workstation, without proving a particular provider fault. Raw results are in local `/tmp/newdrugs-external-results.json`.

The founder requested a full code review of the performance pass; see [review](REVIEW-2026-09-27.md). Host changes and production rollout were paused during that review.

## Follow-up diagnosis, 23:23 UTC onward

The founder again reported slow loading or no load. Fresh read-only checks reproduce the incident independently of the browser:

- Public DNS consistently resolves to `24.144.121.19`, including Cloudflare and Google resolvers. The HTTPS certificate validates and expires December 24, 2026. DNS resolution from the workstation is fast even when TCP connection establishment fails.
- Prod and dev each failed one of four consecutive HTTPS health probes at the eight-second connection deadline. Other samples connected after 3.2 to 4.4 seconds or completed normally. An earlier prod health probe spent 7.39 seconds establishing TCP. Unrelated HTTPS controls from the same workstation completed in 0.08 to 0.30 seconds.
- Direct-IP socket probes show the same intermittent failure on ports 22, 80 and 443. All three timed out in the first simultaneous sample; later samples varied between about 20 milliseconds and 2.2 seconds. The concurrent `1.1.1.1:443` control connected in 23 to 39 milliseconds throughout. This rules out a problem limited to HTTP, TLS, DNS or application routing.
- A fresh independent Globalping measurement at 23:26:26 UTC failed from all three locations: Los Angeles and Falkenstein timed out establishing TCP; Buffalo established TCP after 8.75 seconds, then timed out during TLS. Each test reached its 15-second deadline. The raw result is `/tmp/newdrugs-external-results-2328.json`, measurement `2Rn47lsaEnuNI4l3S00021DP4`.
- On the droplet, nginx served the production health endpoint through local HTTPS in 0.186 seconds. Both app health checks returned `ok:true`. Production still points to `20260927173600978`; dev points to `20260927224311748`. The running database unit is `newdrugs-mongo`, not `mongod`. The separate production worker is inactive because production is still the older combined-process release.
- The host has about 3.0 GiB available memory, no swap use and 16 GiB free disk. Sampled CPU idle time was 67 to 93 percent; steal time was 2 to 12 percent. Interface error/drop and TCP listener overflow/drop counters were zero. These observations do not indicate application load or resource exhaustion as the cause.
- Another eight-packet gateway sample lost five replies; received replies ranged from 0.57 milliseconds to 2.20 seconds. A direct-IP outbound HTTPS request to `1.1.1.1` timed out establishing TCP after eight seconds. An unauthenticated Spaces request timed out resolving DNS. The gateway sample alone does not establish a general packet-loss rate, but the independent inbound and outbound TCP failures corroborate a lower-level transport problem.

Diagnosis: the demonstrated failure is intermittent transport loss or delay on the droplet's external network path, before requests reach the app. A VM host, virtual NIC or provider network problem is the leading explanation; guest observations do not identify the exact faulty component. The provider's [status page](https://status.digitalocean.com/) reported all systems operational, which does not exclude a single-droplet fault. Successful reloads between failed probes do not establish recovery.

No deployment, reboot, service stop, network configuration change, credential change or support contact was performed during this follow-up. Runtime changes remain paused. A controlled move of the existing production release/data to a separately validated host is a possible recovery path if provider-side repair is not pursued; it has not been performed or approved by this diagnostic request.

## Recovery, September 28

With explicit approval for the replacement and temporary overlap, production and dev moved to NYC3 Droplet 604194887 (167.172.21.42). Final writes were frozen on the source before exporting and restoring 4,494 documents. Content hashes matched for 117 non-TTL collections. Source APIs/workers were stopped and disabled before the replacement became authoritative. Public DNS switched around 00:23 UTC.

New-host direct and independent external checks returned 200 in approximately 0.09–0.35 seconds. The founder confirmed fast access. The underlying fault on the old host remains unidentified; moving the workload avoided that path. Some recursive DNS caches continued reaching the impaired old host. Its nginx now forwards to the replacement, with verified TLS depth 5 after correcting an initial bridge 502.

Reviewed application fixes were then deployed as v0.30.1. Both stages have separate bounded workers and private search services. Production media migration completed for 537 files without failures, and all 507 Log sources were indexed. The founder approved old-droplet deletion after DNS clears, no earlier than 01:23 UTC. Deletion has not yet occurred.

## Old-host retirement complete

At approximately 01:28 UTC September 28, both public DNS resolvers and authoritative records pointed to the replacement, all required target services were active, source writers remained stopped, and repeated public/direct-IP production health checks passed. The approved deletion of Droplet 603479023 was accepted with HTTP 204 and subsequently verified with HTTP 404; replacement 604194887 remained HTTP 200. Temporary proxy trust was removed from replacement nginx, which passed validation and reloaded successfully. Migration exports/manifests and old-host diagnostics remain private for recovery. The original host fault itself remains unproven.
