# Performance pass review, September 27, 2026

Review baseline: `9af510f`, immediately before implementation. Scope includes `3c7f91b`, `b18bf2a`, `1070b04`, `26e07dd` and the uncommitted timeout/configuration changes. This covers application, shared contracts, CLI, frontend, workers, deployment, search, billing summaries and object storage. Production remains v0.29.2; this review is not a deployment or a claim that the findings have been fixed.

Resolution: all ten findings below were addressed and shipped in v0.30.1 on the replacement host. Validation passed 25 local regression checks and 106 isolated cloud database checks. The findings remain below as the audit record, not outstanding tasks. Infrastructure recovery is documented separately in INCIDENT-2026-09-27.md.

Fixes: activation rollback now covers startup failures; readiness requires a positive PID on the current host; closed SSE initialization creates no timers; authoritative Log lists and explicit invalidations evict stale previews; memory proofs hash content rather than social counters; transient push authorization/title failures retry; notification history uses four bounded indexed candidate pages with explicit partial unread counts and continuation; calendars use one admitted range aggregate with limited indexed day branches; contacts seek two indexed streams with a 200-candidate page budget; idle agent polling does not write an admission fence. The unsupported global address-timeout workaround was removed. A shared 2,816 MiB app/search memory ceiling and per-stage ceilings preserve room for the existing 500 MiB Mongo ceiling and the OS.

## Findings

### 1. P1: worker startup failure bypasses deployment rollback

Location: `scripts/deploy.mjs:36–58`, especially the new worker start at line 49.

The activation shell uses `set -e`, switches `current` to the new release, restarts the API, then starts the worker. If `systemctl start newdrugs-worker@…` returns nonzero, the shell exits immediately. The rollback at the end is never executed. Production can remain on a partially activated release with its background processing stopped.

Reproduction: executed the actual activation template against disposable local directories and stub service commands, making only worker startup fail. Result: exit 1, `current` still points to the new release, rollback false. No real services were touched. API restart failures also need the same recovery coverage; that portion predates the new worker handling.

Fix: use an activation failure trap or explicit checked activation block covering every step after the previous release is captured. Restore both services and the previous release, with bounded readiness deadlines.

### 2. P1: a dead worker can pass the new readiness check

Location: `server/workerStatus.ts:2–10`, called from `scripts/deploy.mjs:53–54`.

`MainPID=0` means there is no running main process. The checker interprets zero, missing or invalid numeric PID as a wildcard through `!pid`. Any recent worker heartbeat can satisfy readiness, including one left by a crashed process. This can report a successful release while the worker is down.

Reproduction: passed `--require-worker 0` with a recent heartbeat from another PID. The checker exited successfully.

Fix: require a positive integer PID, verify the systemd service is active, and match that exact process. On multi-host deployments also match instance/host identity, not PID alone.

### 3. P2: disconnecting during SSE initialization leaks timers

Location: `server/liveState.ts:137–139`.

A client can disconnect while the initial shared projection is awaiting the database. `close()` runs before the heartbeat and expiration timers exist. Once the projection resolves, the function creates both timers despite the closed connection. Later `close()` calls return immediately, leaving the heartbeat interval alive indefinitely. Reconnection churn accumulates timers and retained response closures.

The heartbeat race also exists in the baseline. This pass retained it and added the expiration timer to the same vulnerable path. It is an inherited reliability defect exposed by the review, not a newly introduced explanation for today's outage.

Reproduction: disconnected during a deferred initial projection, completed the read, then called `stopLiveState()`. Two timers remained.

Fix: return if closed after the awaited initialization, before creating either timer. Cover shutdown and failed projection paths too.

### 4. P2: deleted hangouts survive in Grid/List through cached previews

Location: `src/LogPanel.tsx:169–179` and the hidden calendar invalidation path.

Grid/List always unions calendar previews with authoritative list results. The retained calendar is hidden in these layouts, so its refresh is deferred. After deletion, the list correctly removes the entry, but the old preview is added back by the union. The card can remain visible until the calendar is revisited or the page reloads.

Reproduction: loaded a calendar preview, switched to Grid, emitted a deletion invalidation, and returned an empty authoritative list. The deleted card remained rendered.

Fix: evict explicit removals from shared preview state immediately, including while a layout is hidden. Track which ranges authoritative list results cover so cached previews cannot resurrect unavailable entries. Preserve the instant layout switch.

### 5. P2: unrelated social activity invalidates durable agent memory

Location: `server/agentMemory.ts:23–31`.

Source proofs hash the entire operation response. A post response includes like/reply counts and caller-specific state such as saved/liked, alongside its actual content. A new like therefore changes the proof and silently omits a core note even though the human-authored source did not change.

Reproduction: a core note citing a post was returned initially; changing only `likeCount` from 0 to 1 caused the same note to disappear from core context.

Fix: hash a stable, source-specific content projection or content revision. Continue checking current authorization separately. Do not include counters or viewer presentation state in evidence identity.

### 6. P2: transient Log lookup failures permanently discard push notifications

Location: `server/push.ts:88–89`.

The new title lookup catches every error and marks the outbox event `skipped`. A Mongo timeout or temporary internal failure is treated as revoked access, so the event is never retried even if its recipient and source remain valid.

Evidence: direct control-flow review. This failure branch was not exercised against the live provider or a production notification.

Fix: skip only explicit unavailable/forbidden source results. Let transient errors retain the pending event and normal retry behavior.

### 7. P1 at scale: notification projection still performs history-sized work on bootstrap

Location: `server/notifications.ts:22–30` and `server/liveState.ts:readLiveState`.

Unread totals run the eligibility lookup pipeline over every matching unread record before `$count`. The new pipeline joins authors, Log entries and their members. The 100-item display limit does not bound those count queries. This runs in bootstrap and live-state projection; exceeding the five-second aggregate deadline can fail bootstrap or close a live connection. Large unread histories become an account-level availability problem.

Evidence: aggregation shape and call path. No large production load test was run, and this is not established as the cause of today's incident.

Fix: maintain eligibility-aware unread summaries, with mutation/revocation repair, or design a bounded count presentation. Page and reauthorize displayed records without joining an entire unread history on each refresh.

### 8. P2: compact calendar responses still amplify database work

Location: `server/log.ts:96–113`, `src/useLogCalendarData.ts:15–18`.

Each 35/42-day request launches one aggregate per day. The frontend permits two range requests concurrently, so its first pair can schedule 77 aggregates before ancillary reads. The shared calendar gate permits four active jobs and 256 waiting jobs. Four simultaneous cold clients can exceed that queue even before a large user base exists. Once one job is rejected, already queued sibling work continues although its request cannot succeed.

Evidence: request sizing and gate arithmetic. Actual latency under concurrent real database traffic remains unmeasured; the existing DOM and mocked fanout tests do not establish this capacity.

Fix: batch indexed range reads into bounded date buckets, or admit whole calendar requests and schedule their day reads incrementally with cancellation. Keep dense-day response limits and canonical authorization.

### 9. P2: contact pagination still groups and sorts the whole contact graph

Location: `server/logContacts.ts:37–42`.

The pipeline reads the user's maintained contacts, unions accepted connections, groups all identities, applies the cursor, sorts, joins user records and only then limits the response. The maintained graph removes the hangout-history scan, but this is not an indexed keyset page. Work still grows with the person's entire graph on every page, especially when a text filter rejects most results.

Evidence: pipeline ordering. No maximum-contact benchmark was run.

Fix: materialize the friend/co-attendee union with stable sortable keys, or independently page the indexed sources and perform a bounded merge. Add a measured query-work budget, not only a result limit.

### 10. P2: idle agent admission continuously writes to Mongo

Location: `server/agentAdmission.ts:9` and `server/agent.ts:516`.

Every 500 ms admission attempt increments the global transaction fence before checking whether any job exists. One idle worker therefore attempts about 172,800 fence writes per day. Both stages double that, before other maintenance work. This adds avoidable journaling and replication work to a performance-focused change.

Evidence: unconditional update plus polling interval. This may contribute background disk activity, but it does not establish the cause of TCP connection stalls, which persisted with the new worker stopped.

Fix: use a cheap candidate precheck or notification-driven wakeup before acquiring the transactional fence. Recheck capacity and eligibility inside the transaction so concurrency safety is preserved.

## Operational corrections

- The global five-second address-attempt timeout in `server/config.ts` and the service command lines was an incident workaround. The comment claiming Node's default caused the problem is not established by the evidence. Do not ship it as a proven fix. A larger address fallback delay can itself slow connections when the first address is unreachable.
- Individual service memory ceilings are not a whole-host memory guarantee. The two APIs, two workers and two search instances can collectively exceed the available 4 GB once Mongo and the OS are included. Current low usage is not evidence of peak capacity. Assign a measured host budget before claiming scaling readiness.
- Successful `/api/health` checks are insufficient to close this incident. Public TCP/TLS establishment and outbound provider/storage connectivity must remain reliable too.
- Live dev Log search still fell back to keywords during this incident. Do not claim live semantic validation passed. Previously successful synthetic Qdrant and object-store probes prove those contracts, not continuing network reliability.

## Review and validation coverage

Inspected the changed paths for live events and leases, request limits, worker admission/lifecycle, database indexes, incremental search replication, Log membership and projection, memory authorization/revisions, attachment indexing, object lifecycle/range delivery/migration, billing writers and summaries, scheduler conversion, calendar/layout caching, notification routing, shared schemas, CLI and release tooling. Existing integration tests cover many happy paths and ownership/concurrency cases, but missed the failure paths above.

The local diagnostic harness lives in ignored `.data/review/`. Four isolated Vitest reproductions and one activation-shell simulation confirmed findings 1–5. They intentionally assert the observed defects; they are not passing regression tests for fixes. They used no live database, provider requests, social actions or user credit. No new capacity benchmark was run on the shared production host.

The source authorization checks and immutable object-write approach remain in place. The fixes above have passed negative-path regressions and live dev validation, then the authorized production release. These tests establish correctness and bounded work for their stated workloads, not a million-user capacity claim.
